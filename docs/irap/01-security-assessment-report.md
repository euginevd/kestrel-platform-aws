## 1. Executive summary

### 1.1 What was assessed

The Kestrel AWS Landing Zone — the multi-account AWS foundation into which Kestrel Digital
deploys workloads holding Australian Government data up to PROTECTED. The assessment covered
the organisation structure, policy instruments, identity, network fabric, logging and
evidence plane, and the delivery pipeline, across three layers: AWS as infrastructure
provider (Layer 1), Kestrel's own landing zone (Layer 2), and the third parties the system
depends on (Layer 3).

47 controls were sampled from approximately 1,101 in the June 2026 ISM release.

### 1.2 Overall observation

The landing zone's design is **materially stronger than is typical** for an organisation of
this size operating at PROTECTED. Several controls — the archive key policy's
administration/use separation, the treatment of source silence as an alarmable condition,
the deliberate absence of any human access path to the log archive, and an exception
register that fails a plan when an exception outlives its expiry — reflect a level of design
maturity that would be credited in any assessment.

The weaknesses identified are concentrated in two patterns rather than in architectural
deficiency:

1. **Claim precision.** In several places the system's documentation asserts a property more
   broadly than the configuration delivers it. The clearest instance is a statement that no
   long-lived credentials exist anywhere in the estate, alongside a registered long-lived
   GitHub credential.
2. **Assurance asymmetry.** Controls Kestrel implements are documented and evidenced to a
   high standard. Controls Kestrel *depends on others to implement* — the identity
   provider's approval workflow, the credential vault's own custody, tenant security
   documentation — are asserted rather than evidenced.

### 1.3 Key weaknesses the entity should be aware of (IRAP-AR-0032)

Stated at the front of this report, as the framework requires:

**First — the brownfield account population.** Approximately 60 accounts, the numerical
majority of the estate, sit in an OU carrying only organisation-root controls. They do not
carry the network containment layer that the System Security Plan describes for the estate.
**No examined object establishes whether any of these accounts holds PROTECTED data.** Until
that question is answered, neither the entity nor an authorising officer can size the
exposure. This is the most consequential unknown in the assessment.
([FIND-K07](03-findings-register.md#find-k07))

**Second — a standing broad privilege grant.** The `WorkloadDeploy` permission set grants
`PowerUserAccess` to a named group, deferred for replacement on a business condition that no
mechanism detects or enforces. ([FIND-K03](03-findings-register.md#find-k03))

Both are disclosed by the entity in its own risk documentation. Disclosure is credited; it
does not close either gap.

## 3. System overview (IRAP-AR-0037, IRAP-AR-0038)

### 3.1 Purpose and architecture

Kestrel Digital hosts Australian Government data as a SaaS provider. The landing zone is the
foundation into which every workload deploys, so that a new workload inherits identity,
guardrails, logging and networking at creation rather than acquiring them later.

The organisation is structured by policy rather than by business unit:

```text
Root (Kestrel Organisation)
├── Security             log archive + security tooling (delegated administration)
├── Infrastructure       network core, shared services, state backend
├── Workloads
│   ├── Prod             customer-facing, PROTECTED — one account per tenant
│   └── Non-Prod         dev, test, staging
├── Sandbox              time-boxed experimentation
├── Transitional         ~60 brownfield accounts, detective posture (see FIND-K07)
└── Suspended            quarantine — deny-all
```

An account's OU determines the controls it inherits. Policies attach to OUs rather than
accounts, so an account created tomorrow inherits enforcement before its first resource
exists.

### 3.2 Technologies and their function (IRAP-AR-0028)

| Technology | Function in this system |
|---|---|
| **AWS Organizations** | Account hierarchy and the attachment point for all policy instruments |
| **Service Control Policies (SCP)** | Deny-based guardrails limiting what principals *within* the organisation may do |
| **Resource Control Policies (RCP)** | Deny-based guardrails limiting what principals *outside* the organisation may do to Kestrel resources |
| **IAM Identity Center** | Federated access broker; resolves Entra group membership to AWS permission sets |
| **Microsoft Entra ID + PIM** | Workforce identity, MFA, Conditional Access, and just-in-time privilege elevation |
| **AWS Cloud WAN** | The network fabric; a segment per security zone, replacing per-Region transit gateways |
| **AWS IPAM** | Authoritative CIDR allocation; VPC creation without an IPAM pool is denied |
| **AWS Network Firewall** | Inspected, logged egress — one path per Region |
| **AWS CloudTrail** | The authoritative record of API activity; management, data and network-activity events |
| **AWS Config** | Configuration state over time; two recording speeds by resource type |
| **S3 Object Lock (COMPLIANCE)** | Write-once retention that no principal, including root, can shorten |
| **AWS KMS** | Customer-managed keys; the archive key policy separates administration from use |
| **Amazon Security Lake** | Normalises log sources to OCSF, providing a schema-based seam to the SOC |
| **Amazon Athena** | Query path over the archive, independent of the SOC's platform |
| **GuardDuty / Security Hub / Inspector / Macie / Detective** | Threat detection, posture management, vulnerability scanning, data classification, investigation |
| **Terraform + GitHub Actions (OIDC)** | Declarative change delivery with no long-lived cloud credentials |

### 3.3 Data flows

**Evidence flow.** Every account emits CloudTrail events, Config items, VPC flow logs,
Resolver query logs and Session Manager recordings to a single Object-Locked bucket in
`log-archive`, encrypted with a customer-managed key. Security Lake normalises sources to
OCSF in parallel — collected at source, not copied from the archive. The SOC reads the
normalised copy through a subscriber; Athena queries the archive directly. Cross-Region
replication maintains a Melbourne copy under the same retention.

**Administrative access flow.** Staff authenticate to Entra ID from a managed compliant
device, elevate through PIM where privilege is required, and are resolved by Identity Center
to a permission set in a target account. Sessions are logged; interactive instance access is
recorded.

**Deployment flow.** A pull request passes CODEOWNERS review and a credential-free checks
stage, merges to `main`, and is applied by GitHub Actions assuming an OIDC role. No human
path to production infrastructure bypasses this route.

### 3.4 Deviations from technical guidance (IRAP-AR-0030)

The entity deviates from ASD's Blueprint for Secure Cloud in that it does not use the
Blueprint's Azure-centric patterns, and deviates from AWS's Control Tower / Landing Zone
Accelerator in favour of a Terraform-native implementation on AWS Organizations
([ADR-0003](../adr/ADR-0003-engine-and-state.md)). Both deviations are documented with
reasoning. The resulting architecture remains aligned to the AWS Security Reference
Architecture, and the deviations do not, in themselves, weaken control implementation.

## 5. Security strengths

Recorded per IRAP-AR-0045, which requires the report to articulate strengths as well as
weaknesses.

**The evidence plane is the system's strongest characteristic.** Object Lock in COMPLIANCE
mode for seven years is set at bucket creation, with lifecycle rules deliberately aligned to
the lock so the two cannot disagree. Crucially, the encryption key policy separates
administration from use so that no principal holds both — recognising that an archive
encrypted with a key someone can disable is deletable by another name. This is a failure
mode most Object Lock implementations do not address.

**Absence of signal is treated as a signal.** Source-silence alarms configure missing data as
breaching, correctly recognising that a stopped log source produces no datapoints rather than
zeros. The trail-delivery alarm deliberately uses CloudTrail's own delivery-failure metric
rather than a log query, on the reasoning that the one alarm which must never depend on the
trail is the trail-failure alarm. These alarms are deliberately Kestrel-owned, because a
provider cannot detect its own feed going quiet.

**The identity model removes standing privilege.** No IAM users and no long-lived AWS access
keys exist. Elevation groups hold no standing grant and are populated only during an
activation. The `log-archive` account carries no permission set assignment at all — the
account holding every log is one nobody can log into.

**Governance mechanisms are self-enforcing.** The exception register cannot hold an
off-register exception, and an exception outliving its expiry fails the Terraform plan. This
mechanism is what surfaced [FIND-T03](03-findings-register.md#find-t03) — the register
worked exactly as designed.

**Prior findings were remediated at the right depth.** The entity's own FIND-012 concerned a
retention gap on the log replica. The remediation added not only the missing configuration
but the missing *test*, so the coverage persists.

**Threat modelling drives configuration.** The decision to record CloudTrail network-activity
events, on the reasoning that the threat is someone reading data through a private path with
valid credentials rather than someone changing configuration, is an unusually well-targeted
control choice.

## 7. Risk management processes used by the entity (IRAP-AR-0015)

The entity maintains a Security Risk Management Plan documenting 13 risks with inherent and
residual ratings, treatment approach, named owners and, where treatment is incomplete,
expiry dates. Acceptance authority is defined by residual band, with High residuals
requiring written CISO acceptance and system owner endorsement, recorded as signed
architectural decision records.

The assessor observes that the entity's risk process is **honest in a way that is
uncommon**: the brownfield population is rated High residual with treatment explicitly
incomplete, rather than being rated down to Medium on the strength of a plan. The SRMP
states that rating it Medium before accounts have graduated would be self-deception. That
posture materially assisted this assessment.

Exceptions are managed on a machine-reconciled register with mandatory owner, reason,
compensating control and expiry.

Per IRAP-AR-0034, this report does not rate the entity's risks or endorse its ratings; it
records the process and notes where the assessment's observations may warrant the entity
revisiting a rating — specifically R-09 (data-event scope), where the assessor's view of the
compensating controls differs from the entity's.

## 9. Consumer recommendations from the provider (IRAP-AR-0007)

The framework requires the assessor to gather consumer recommendations from the provider,
evaluate them, and include them.

The entity's documentation contains guidance directed at tenants consuming the landing zone:
that guest OS hardening, patching, application control and application security remain the
tenant's responsibility; that a tenant workload requires its own System Security Plan; and
that Non-Prod accounts are not to hold production data.

**Assessor evaluation.** These recommendations are appropriate and correctly scoped. Two
carry a caveat for consuming entities:

1. The requirement for a tenant SSP is stated but not verified at any point in the vending
   process ([FIND-T07](03-findings-register.md#find-t07)). A consuming entity should not
   assume the platform will detect its absence.
2. The statement that Non-Prod holds no production data is a policy position, not a
   technically enforced control ([FIND-K03](03-findings-register.md#find-k03)). A consuming
   entity should treat it as a commitment it must itself uphold.
